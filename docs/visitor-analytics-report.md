# تقرير تنفيذ Visitor Analytics

تاريخ التنفيذ: 9 أكتوبر 2026. اتنفذت المرحلتان في مشروع الموقع، واتعدّل مشروع الباك إند الموجود في `/Users/muhammadessam/Projects/portfolio-contact-api` لإرسال البيانات الجديدة في Telegram.

## اللي اتعمل

- تسجيل hostname المُحيل فقط، و`utm_source` و`utm_medium` و`utm_campaign` و`ref`. حفظ أول مصدر للزائر في localStorage وفي سجل الزائر، ومصدر الجلسة في sessionStorage وفي Firestore.
- توليد UUID للزوار الجدد والجلسات ومشاهدات الصفحات والأحداث. الاحتفاظ بالـ visitor IDs القديمة ونقل أعدادها من `stats/visitors.users` عند رجوع أصحابها، من غير مسح الخريطة القديمة.
- إضافة `POST /api/track` داخل Next.js. البلد والمدينة والمنطقة من [هيدرز Vercel](https://vercel.com/docs/headers/request-headers)؛ تحليل نوع الجهاز والمتصفح ونظام التشغيل على السيرفر؛ اللغة والمنطقة الزمنية وأبعاد الشاشة من المتصفح.
- نقل **كل كتابات التحليلات** من المتصفح للسيرفر، باستخدام [Firestore REST وOAuth بحساب خدمة](https://firebase.google.com/docs/firestore/use-rest-api)، من غير إضافة dependencies. المتصفح يرسل أحداثًا، والسيرفر يحسب الزيادات؛ لا يستقبل إجماليات من العميل.
- تجميع الكتابات في commit ذري، مع منع تكرار event ID، والتحقق من إصدارات المستندات وإعادة المحاولة عند تعارض الطلبات. النتيجة تشمل إجماليات Telegram الفعلية بعد الكتابة.
- حفظ جلسات في `visitor_sessions` وأحداث في `visitor_events`: visitorId، sessionId، pageId، اسم الحدث، الهدف، المسار، وتوقيت السيرفر. الأحداث القديمة لا يمكن استعادة تفاصيلها؛ عداداتها محفوظة.
- قياس الوقت أثناء ظهور التبويب، وإرساله بـ sendBeacon عند `visibilitychange` و`pagehide` وعند الانتقال بين صفحات التطبيق. تحديث كل دقيقة أثناء التفاعل لتقليل ضياع البيانات لو المتصفح اتقفل فجأة.
- قياس أقصى scroll depth، وتسجيل رؤية Projects وExperience وContact باستخدام IntersectionObserver. كل قسم يُحسب مرة واحدة لكل جلسة.
- تركيب VisitorTracker في root layout لتتبع الرئيسية وصفحات المشاريع، واستبعاد صفحات الأدمن. بدء التتبع بعد التحميل وفي idle، وعزل أعطاله عن العرض والأزرار ونموذج التواصل.
- احترام Do Not Track: إيقاف التحليلات بالكامل عند `navigator.doNotTrack === '1'`، ورفض التسجيل أيضًا عند وصول هيدر DNT.
- الحفاظ على عدادات الزيارات والأحداث والمشاريع وأزرار المشاريع وتنزيلات CV. لا توجد كتابة Firestore مباشرة من متصفح الزائر.
- إضافة عرض المصادر والمُحيلين ووسوم الشركات والدول والمدن والأجهزة والمتصفحات وأنظمة التشغيل في الأدمن، ومتوسط الوقت المرئي لكل صفحة، ومتوسط أقصى تمرير لكل جلسة، ونسب وصول الأقسام. الـ timeline يحمل 100 حدث في كل مرة مع زر للأحداث الأقدم.
- تحسين عرض المصادر المتداخلة في سجلات Telegram، وإظهار حقول IP والإحداثيات القديمة فقط كسجلات تاريخية.

## تحديثات الباك إند

اتعدّلت `api/visitor.js` و`api/cv-download.js` و`api/_helpers.js`، واتضافت اختبارات وتوثيق في README.

الإشعار الجديد يعرض البلد والمدينة والمصدر ووسم الشركة والحملة والجهاز والمتصفح والنظام واللغة والتوقيت والشاشة والصفحة وأول مصدر. مسارا visitor وcv-download بقى اتصالهم من السيرفر فقط، ويتحققوا من Bearer secret مشترك. الـ contact endpoint ما زال يستقبل نموذج التواصل من المتصفح.

تم إيقاف تجميع أو إرسال أو حفظ IP والإحداثيات والـ User Agent الخام في الإشعارات الجديدة، بما فيها إشعارات التواصل التي تستخدم نفس الـ helper. لم تُحذف السجلات التاريخية. لا توجد بصمة جهاز أو third-party cookies، ولا تم تركيب PostHog أو Vercel Analytics.

حقول visitor payload:

```text
visitorId, sessionId, isNewVisitor, totalUnique, totalVisits,
source, firstTouch, country, city, region, device, browser, os,
screen, language, timezone, path
```

`source` و`firstTouch` يحتويان: `referrer, utmSource, utmMedium, utmCampaign, ref`.
إشعار CV يستقبل نفس السياق من غير إجماليات الزوار.

## المطلوب منك عند النشر

1. استضافة الموقع كمشروع **Next.js على Vercel** أو سيرفر Node يدعم Next.js. أُزيل `output: 'export'` لأن GitHub Pages لا يشغّل POST Route Handlers. الـ GitHub workflow أصبح للفحص، ولا ينشر إلى Pages. تحديث المحتوى اليومي محفوظ باستخدام ISR كل 86400 ثانية، ويحدث بعد أول طلب بعد انتهاء المدة.
2. ضبط `FIREBASE_PROJECT_ID` و`FIREBASE_CLIENT_EMAIL` و`FIREBASE_PRIVATE_KEY` في **مشروع الموقع**. استخدم حساب خدمة بصلاحية `roles/datastore.user`. هذه قيم server-only؛ لا تضع عليها بادئة NEXT_PUBLIC. المثال موجود في `.env.example`.
3. ضبط `VISITOR_NOTIFICATION_SECRET` بقيمة عشوائية طويلة **ومتطابقة في المشروعين**. الباك إند يرفض هذه الإشعارات لو الـ secret غير مضبوط أو مختلف. الـ secret لا يصل إلى المتصفح.
4. التأكد أن `NEXT_PUBLIC_CONTACT_ENDPOINT` يشير إلى `/api/contact` في مشروع الباك إند، وأن الباك إند يحتوي على بيانات Telegram وFirebase الحالية. ضبط `CONTACT_ALLOWED_ORIGIN` على أصل الموقع النهائي، مثل `https://muhammadessam.me`، لاستمرار عمل نموذج التواصل بعد نقل الاستضافة.
5. نشر الـ index الجديد وانتظار جاهزيته، ثم نشر المشروعين ونقل الدومين لاستضافة Next.js. بعد تشغيل نسخة الموقع الجديدة، نشر القواعد التي تمنع كتابات المتصفح وتسمح للأدمن بقراءة البيانات الخاصة:

```bash
firebase deploy --only firestore:indexes
firebase deploy --only firestore:rules
```

`firestore.indexes.json` يحتوي composite index لـ `visitor_events`: visitorId تصاعدي ثم timestamp تنازلي. `firebase.json` يشير إليه. القواعد تستخدم UID الأدمن الموجود بالفعل. حساب الخدمة يعمل بصلاحيات IAM؛ القواعد لا تمنع كتاباته.

أمثلة روابطك:

```text
https://muhammadessam.me/?utm_source=cv
https://muhammadessam.me/?utm_source=linkedin
https://muhammadessam.me/?ref=acme&utm_source=cv&utm_campaign=hiring
```

وسم `ref=acme` يحدد الرابط الذي استُخدم، ولا يُثبت هوية الشركة أو شخص بعينه.

## التحقق

- `npm run lint`: ناجح. تم استبعاد ملفات design-system المولّدة التي كانت تسبب أخطاء lint قديمة؛ كود التطبيق ما زال يُفحص.
- `npx tsc --noEmit`: ناجح.
- `node --test tests/*.test.mjs`: 11 اختبارًا ناجحًا في مشروع الموقع، تشمل الاختبار الموجود سابقًا.
- `npm test` في الباك إند: 5 اختبارات ناجحة، تشمل تنسيق Telegram، رفض الـ secret الخاطئ، عدم حفظ البيانات الحساسة، وفشل Telegram.
- `npm run build -- --webpack`: ناجح؛ build الإنتاج يشمل `/api/track` وصفحات المشاريع. تشغيل `npm run build` مع Turbopack تعطل بسبب منع فتح منفذ في بيئة التنفيذ، لذلك استخدمت Webpack للتحقق من build الإنتاج.
- الاختبارات تغطي أيضًا الجلسات المتزامنة، إعادة المحاولة، منع تكرار الأحداث، IDs القديمة، أولوية المتصفحات، الحقول العربية في Firestore، DNT، تعطل storage، وإرسال beacons.

## حدود وقرارات التنفيذ

- نسب المصادر والأجهزة والأقسام تخص **الجلسات**، وليست عدد أشخاص معروفين. الأقسام تظهر بترتيب الصفحة الحالي: Projects ثم Experience ثم Contact. الوصول قد يقفز بين الأقسام؛ ليس تسلسل تحويل إلزاميًا.
- الطلب المعتاد لحدث يحتاج قراءة جلسة واحدة وcommit واحد. مشاهدة الصفحة تحتاج قراءة الجلسة والزائر، مع قراءة إضافية للعداد القديم عند إنشاء سجل الزائر. تم تقليل رحلات الكتابة إلى commit واحد، وتجنب قراءة إجماليات الزوار في كل زيارة؛ **إجمالي كتابات المستندات القابلة للفوترة أصبح أعلى من النظام القديم** بسبب حفظ الأحداث والجلسات والأبعاد الجديدة، ولم أعتبر تقليل طلبات الشبكة تقليلًا لتكلفة Firestore.
- السيرفر يمنع التلاعب المباشر بمستندات العدادات بعد نشر القواعد، ويتحقق من الأحجام والأحداث والأصل، ويحد الجلسة إلى 600 حدث. نظام تحليلات مجهول لا يمنع بوتًا قادرًا على إنشاء جلسات وطلبات جديدة؛ حماية Vercel من البوتات/rate limiting هي الإجراء التالي إذا ظهر إساءة استخدام.
- التعرف على الأجهزة تقريبي؛ بعض أجهزة iPad في وضع سطح المكتب قد تظهر desktop/macOS. الموقع الجغرافي تقريبي وقد يظهر Unknown خارج Vercel.
- الوقت يبدأ بعد تهيئة التتبع، وقد تُفقد آخر لحظات التفاعل أو أحداث أثناء انقطاع الشبكة. حظر storage أو DNT يوقف التتبع بأمان.
- أبعاد المصادر والمدن تُجمع في `stats/analytics`، على نمط العدادات الحالية. لو زادت القيم المختلفة لدرجة الاقتراب من حد Firestore البالغ 1 MiB، يلزم تقسيم هذه العدادات إلى مستندات منفصلة.
- لا يوجد حذف تلقائي للأحداث أو تغيير للسجلات التاريخية. يلزم تحديد سياسة الاحتفاظ لاحقًا إذا زاد حجم البيانات.
- لم أنشر الموقع أو الباك إند أو قواعد/indexes Firestore، ولم أرسل رسالة Telegram حقيقية أو أكتب بيانات اختبار في قاعدة الإنتاج. التحقق من سلوك التخزين والإشعارات تم باستخدام mocks، ولم يُجرَ فحص بصري للداشبورد أو قياس LCP فعلي.
- مشروع الباك إند المرفق ليس Git repository، لذلك تعديلاته محفوظة على القرص وتحتاج أن تُنشر من هذا المجلد؛ لم أنشئ له repository أو commit تلقائيًا.


تغييرات الموقع محفوظة في commit للتتبع وcommit للأدمن والتقرير. ملف المهمة الأصلي `docs/visitor-analytics-prompt.md` لم أعدّله ولم أضفه إلى commits لأنه كان غير متتبع قبل التنفيذ.
